## 建议优先处理的 10 项

### P01：缩放时重复扫描图像、读取文件元数据（P1）

- 依据：`MainWindow.cpp:987` 的 `onZoomChanged()` 调用 `updateImageInformation()`，继而进入 `formatTitleText()`、`pixelFormatText()`。后者调用 `image.isGrayscale()`。本机 Qt 源码 `qimage.cpp:2743` 确认 24/32 位格式会进入 `allGray()`，最坏遍历整图。RGB 编码但内容全灰的大图会走完整扫描；原生 Grayscale8/16 不需要扫描。
- 同时标题更新重新查询文件大小和修改时间；`ImageCache.cpp:25` 的缓存查询在主线程调用时还会在锁内读取 canonical path、大小和时间。网络目录下尤其值得测量。
- 建议：加载时在后台生成一次格式和文件元数据，缩放仅更新比例字段；保留明确的刷新/文件变更失效机制，不靠反复 stat 保证一致性。
- 延伸：`ImageAnalysis.cpp:35` 在小 ROI 统计前也调用整图 `isGrayscale()`，且这一步没有逐行取消检查；应复用已确定的图像类型。灰度、BGR 等格式可以直接按行统计，减少当前逐行 copy/convert 的分配。
- 验收：同尺寸 RGB 彩色、RGB 编码灰图、原生灰图分别连续缩放，记录 UI 事件延迟；小 ROI 耗时不应随无关的整图面积明显增加。

### P02：目录扫描与缩略图条目创建仍阻塞主线程（P1）

- 依据：`MainWindow.cpp:793` 在主图 `setImage()` 前调用 `DirectoryModel::loadForFile()`；`DirectoryModel.cpp:66` 枚举目录并自然排序；`ThumbnailBar.cpp:150` 为全部文件逐个创建 QListWidgetItem。批量文件去重还使用线性 contains。
- 影响：首次打开万级目录、网络目录、刷新目录时，解码虽在后台，界面仍可能等待目录工作；缩略图图片缓存有界，但列表条目仍随文件数量增长。
- 建议：当前图片先显示，目录后台扫描并以请求版本作废旧结果；列表采用模型和分批布局，路径去重使用集合，并维护路径到索引的映射。
- 验收：1 千、1 万、5 万文件目录的首次可见时间、目录就绪时间和 UI 最长停顿分别记录；期间可继续缩放或打开其他文件。

### P03：预加载绕过缓存预算，且可能重复解码（P1）

- 依据：`ImageCache.h:15` 默认限额 384 MiB；`MainWindow.cpp:1116` 预加载前后各两张，并在 worker 的结果数组中保留全部成功解码图片，整个批次完成才插入缓存。没有在途解码请求共享。
- 影响：384 MiB 是该缓存的上限，并非进程内存上限。假设每张 10000×10000、4 字节/像素，单张约 381 MiB，四张结果本身约 1.49 GiB；此数字仅为数据量估算，未包含当前图、处理临时数据、显示资源等，也不是实测峰值。多窗口还会叠加各自预算。
- 建议：根据像素数估计开销，按预算决定预加载数量；大图降低到一张或不预加载；每张完成就交付并释放批次引用；当前查看与预加载合并同一路径的在途请求。进程内多窗口可共享不可变解码缓存，跨进程则分别受限。
- 验收：大图连续翻页、反复回看、多窗口场景记录峰值内存、命中率、重复解码次数；超预算图可正常查看但不盲目预加载邻图。

### P04：旧任务只丢弃结果，仍会继续消耗资源（P1）

- 依据：加载、预处理、金字塔主要用 generation 防止旧结果显示；`ImageProcessor::process()`、`ImagePyramid::build()` 和预加载批次没有协作取消。多个 QtConcurrent::run 调用使用默认线程池。窗口和控件析构中存在 waitForFinished。ROI 分析已有逐行取消，可保留并扩展其模式。
- 影响：快速跳图或连续调参数时，新请求可能等旧工作做完；多个窗口可让预加载、金字塔等与当前解码竞争。关闭窗口也可能等待不可取消的解码或 I/O。
- 建议：前台解码与低优先级工作分配明确的并发预算；算法阶段、缩放层级及预加载每张之间检查取消；新请求优先。解码器内部不可中断时明确保留生命周期，不能强杀工作线程或析构仍被使用的对象。
- 验收：连续跳转后只显示最后请求，统计过期工作耗时、当前任务排队时间，以及关闭窗口等待时间。

### P05：每生成一张磁盘缩略图，都扫描整个缓存目录（P2）

- 依据：`ThumbnailCache.cpp:58` 每次成功 store 都调用 prune；prune 枚举、按时间排序所有 PNG 并重新求总大小。256 MiB 磁盘上限已经存在，问题是清理频率。
- 影响：缓存文件很多时，重复目录扫描会拖慢新缩略图出现，增加磁盘工作。虽然在后台，也会和图片读取争用资源。
- 建议：增量记录体积，按批次/阈值触发清理，定期校准；多窗口共享清理调度。保留硬上限和异常中断后的恢复机制。
- 验收：不同缓存规模下测冷缓存生成速率、目录枚举次数和最终磁盘占用。

### P06：保存结果在主线程编码，随后清空全部图片缓存（P1）

- 依据：`MainWindow.cpp:875` 同步调用 `saveImage()`，内部 QImageWriter 编码并提交 QSaveFile；完成后清空图片缓存、刷新目录、重建缩略图条目。
- 影响：大图 PNG/TIFF 或慢磁盘保存可能让窗口暂停响应；保存一张图使邻图缓存全部失效，影响随后的翻图。
- 建议：后台保存一份不可变结果快照，显示保存状态，保留现有原子写入；仅失效目标文件相关缓存并增量更新目录。明确保存中重复操作、关闭窗口和覆盖同一文件的规则。
- 验收：保存时仍可浏览；切图不改变正在保存的内容；失败不损坏旧文件；保存后邻图缓存仍命中。

### P07：普通打开路径重复设置主图，触发重复显示构建（P1）

- 依据：`MainWindow.cpp:813` 先调用 `view_->setImage(originalImage_)`，未启用预处理时又在 `showOriginalImage()` 中调用一次。`ImageView::setImage()` 会清空金字塔、重建 QPixmap 图元、请求金字塔；异步结果需要经过事件循环回来，第一次请求可能立即被第二次设置作废。
- 影响：重复显示资源构建及金字塔任务作废是确定的调用路径；具体 CPU/内存成本取决于格式和 Qt 内部共享，不能把每次 QImage 赋值都当成深拷贝。
- 建议：每次有效图片只提交一次显示更新，复用未变化的图元和金字塔；按实际缩放需要构建层级。先修此处，再评估渐进预览或瓦片解码，避免立即引入复杂渲染重构。
- 验收：一次普通打开只有一次主图提交；大图首次显示和最终清晰显示分别计时；检查保留缩放/查看位置的既有行为。

### P08：高位深图的显示值与原始测量值需要明确区分（P1，能力边界）

- 依据：README 已说明处理/统计使用 8 位，并未承诺原始 16 位分析。光标提示 `ImageView.cpp:757` 使用 QColor::red() 等 8 位值；分析采用 256 档，预处理转换为 Grayscale8/RGB888；OpenCV fallback 拒绝非 8U。
- 影响：即使 Qt 能打开 16 位灰图，用户也可能把显示的 0–255 读数误当成原始像素值。不是所有 16 位文件都无法打开，而是全链路原始精度不完整。
- 建议：近期在界面明确标记“8 位显示值”，防止误解；若定位覆盖工业相机原图，再独立规划原始 16 位取样、统计、显示映射与导出，避免把窗宽窗位后的值混作原始值。
- 验收：已知 16 位样图（含接近的低位差异）验证原始值和显示值的语义；不支持的处理应明确说明转换行为。

### P09：透明图片进入预处理后丢失 Alpha（P1，正确性）

- 依据：`ImageProcessor.cpp:30` 将输入转换成 Grayscale8 或 RGB888，结果只输出 1/3 通道；未保存、重附加透明通道。即使开启预处理且所有参数为默认值，也会经过这条转换路径。
- 影响：透明 PNG/WebP 的处理结果及导出会变成不透明，不能仅用颜色看起来一致判断处理正确。
- 建议：颜色处理与 Alpha 分开保留；定义滤波边缘及灰度输出的透明语义。默认参数应尽可能直接返回输入；不支持的组合应明确提示。
- 验收：全透明、半透明和彩色边缘图，默认处理后 Alpha 不变；导出重读检查 Alpha 与边缘颜色。

### P10：README 的安装能力说明互相矛盾（P2）

- 依据：README 开头和打包段已经介绍 v2.3.0 安装 EXE，仓库存在 Inno Setup 脚本与 CI 安装包发布步骤；“验证与已知限制”段仍写“没有安装程序”。
- 影响：用户可能误判安装能力，开源下载说明缺乏一致性。
- 建议：统一下载、安装、版本和已知限制；将代码签名、自动更新分别描述，不与已具备的安装器混写。本轮没有在线核验远端附件是否可下载。
- 验收：按 README 在干净 Windows 环境走一遍下载、安装、启动、卸载路径，发布时核对真实附件和校验值。

## 建议执行顺序与测量方式

1. 首批做 P01、P07、P02：直接减少日常缩放和打开的前台工作；P09 可作为独立正确性修复。
2. 再做 P03、P04、P06：控制大图峰值内存、过期计算及保存阻塞。
3. 随后做 P05、P10；P08 先明确显示语义，完整高位深能力单独确定范围。

当前已有解码日志和处理耗时，但这些不等于“按下切图键到真正看见新图”的端到端耗时。建议增加可关闭的诊断采样，分别记录请求、排队、解码完成、目录就绪、首帧绘制、完整显示；汇总中位数和 P95，同时记录峰值内存、缓存命中率及主线程最长事件延迟。

样本包括：现有 2448×2048 BMP 工作流、较大 JPEG/PNG、RGB 编码灰图、原生 16 位 TIFF、透明图；本地 SSD/网络目录；冷/热缓存；单窗口/多窗口；连续翻图/缩放/保存。冷缓存定义需区分应用缓存与系统文件缓存。对比应使用相同机器、版本配置和样本，不依据一次运行承诺性能提升。
